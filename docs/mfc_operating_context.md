# MFC 운영 조건과 분석 전제

최종 갱신: 2026-10-16

이 문서는 사용자가 설명한 현재 센터 운영을 다른 에이전트가 동일하게 이해하도록
정리한 기준 문서다. 향후 관심 대상은 동일 SKU의 로케이션 분산과 출고 시 할당된
로케이션에 따른 동선 분산이다. 사용자는 ‘압축진열’을 제안했으며, 패킹 구역과의 거리,
수직 진열, 장바구니 구성의 불확실성, 현행 히트맵 관리와 유사 상품의 인접 진열 위험도 설명했다.
아래 운영 설명은 사용자 제공 정보이며, 원본 데이터로 검증한 결과와 구분한다.

**2026-10-16 최신 요청:** 기존 렉 정보와 레이아웃을 이용해 주문 1건의 동선 산식을
설계한다. 복잡한 그래프 계산 대신 왕복을 고려한 수직 이동 ×2, 짧은 수평 이동 생략,
레이아웃별 보정 등을 검토하려는 요청이다. 이는 모델링 선호이며 현행 작업 경로에 관한
새로운 확정 사실은 아니다. 후속 답변에서 사용자는 **수직 이동은 각 구역 안쪽으로 들어가는
방향이며 렉 선반 높이는 생략**한다고 확인했다. 그림의 Y축과 동일하다는 뜻으로 해석하지
않는다. 짧은 수평 이동의 생략 기준·보정값은 아직 미확인이다.
[단순 동선 산식 초안](mfc_order_distance_model.md)에 가정과 제안식을 기록했다.
사용자는 과거 유사 산식을 만든 경험이 있으며, 이번 초안을 발전시키는 방향에 동의했다.
간결함과 여러 시스템에 적용하기 쉬운 구조를 선호한다. 이는 접근법 채택이며 실제 경로·
보정값·정확도가 확인되었다는 뜻은 아니다.
후속 요청으로 **9월 데이터의 주문별 거리 비용 계산, 렉 방문 빈도 히트맵,
최장 거리 주문과 평균 비용·대표 주문의 방문 위치 표시**까지 범위가 확대되었다.
이어 평균 거리 대표 주문을 10개로 확대해 달라는 요청을 받았다. 평균 비용과의 절대 차이,
요청 시각, 주문번호 순으로 선정하고 각 주문의 방문 렉을 표시한다.
자료에 있는 9월 기간은 9/1~9/27이며, 아래의 과거 구현 범위와 구분한다.
사용자는 공통 출발·도착 지점이 **B와 C 사이이며 B09, C04~C06과 가장 가까운 곳**이라고
확인했다. 추가로 **A 입구는 A06~A08 사이, B에서 A로 향하는 출구는 B04 방향**이며,
**A–B–패킹–C–D 순서여서 A는 B를, D는 C를 반드시 통과**한다고 확인했다.
정확한 대표 좌표·통로 길이·구역 사이 연결거리는 아직 미확인이다.

**현재 작업 범위:** 2026-10-14에는 설명 기록만 요청했으며, 2026-10-15에는 사진과 context를
바탕으로 레이아웃을 배열로 표현하고 단순 동선 계산에 사용할 수 있도록 준비하는 작업을 요청했다.
현재 A·B·C·D 기준, 존·복도·렉까지만 표현, 실제 미터 대신 상대적인 칸 수를 사용하는 조건이다.
입출고 전체 집계, 개선 효과 검증과 감지 로직 작성은 아직 시작하지 않는다.
[렉 단위 배열 설계안](mfc_layout_array.md)에 확인된 조건과 미확인 위치 정보를 정리했다.
후속 요청에서 사용자는 **센터 레이아웃을 배열과 그림으로 표현하는 코드만** 필요하다고
명시했다. `notebooks/08_mfc_layout.ipynb`는 레이아웃을 표시하며, 최신 요청에 따라
5절에서 9월 출고 로케이션 목록을 읽어 렉 단위 스케일을 조정한다.
출고량 히트맵·동선 계산은 구현하지 않는다. 미관측 번호를 실제 렉으로 확정하지 않는다.
추가 상온 사진과 사용자 확인에 따라 C 히트맵 뒤로 이어지는 D 랜덤 진열 구역을 반영했다.
후속 확인에 따라 상온의 기존 X=0~33 폭을 유지하고 Y=28·29에 X=27까지 렉을 추가한다.
렉 사이 교차 통로를 유지하며, 히트맵 상세 정보는 레이아웃 확정 후 사용자에게 받는다.
현재 지도 배열의 렉 기호는 사용자 요청에 따라 A 존은 `A`, B 존은 `B`로 표시한다.
이 변경은 기존 `R` 기호의 존별 구분이며 렉 위치나 로케이션 번호 변경을 뜻하지 않는다.
최신 요청은 **2026년 9월 출고의 렉 코드를 참고해 알파벳 한 칸을 렉 하나로 맞추는 것**이다.
처음 언급한 10월은 9월로 정정되었다. 레이아웃 조정을 위한 로케이션 목록 추출은
현재 작업 범위에 포함하며, 출고량 히트맵·개선 효과·동선 계산은 수행하지 않는다.
냉동 A·냉장 B의 렉 단위 지도는 노트북 6절에서 각각 확대 그림으로도 저장한다.
2026-10-15 후속 요청으로 렉 정보와 레이아웃을 다른 노트북에서 쓰도록 버전별 구조
(`references/mfc_layout/layout_2026-09.json`, `load_layout`)로 저장했다. 다음 목표는
주문별 방문 렉을 점으로 표시하는 것이며, 최종적으로 홀짝·번호 방향 등 레이아웃 규칙을
바탕으로 계산한다. 사용자는 레이아웃이 큰 구조를 유지하면서 시기별로 조금씩 바뀌었다고
설명했다. 각 변경의 시점과 내용은 아직 받지 않았다.
이어서 `notebooks/09_order_picks_on_layout.ipynb`를 만들어 주문 1건의 할당 렉을 현재
레이아웃 위에 점으로 표시한다(`show_order("주문번호")`). 사용자 선택에 따라 대상은
**2026-08-10~09-27** 출고뿐이다. 경로·이동거리·방문 순서는 계산하지 않는다.
`notebooks/10_rack_visits_by_hour.ipynb`는 조회 기간별(현재 8/10~8/31, 9/1~9/27) 출고를
출고 요청 시각 기준 3시간 구간으로 나눈다. 결과는 `reports/mfc_rack_visits_by_hour/<시작>_<종료>/`에
기간별로 저장한다.
사용자는 과거 레이아웃을 직접 다시 작성하기로 했다. 이를 위해 `notebooks/11_rack_code_history_2026.ipynb`가
2026년 출고의 렉 코드 등장·종료·재등장을 주 단위로 정리하고, 구간별 복도·렉 번호를 현재
레이아웃과 비교한다(`reports/mfc_rack_history_2026/`). 기간별 정리는
[2026년 렉 코드 기간별 변화](mfc_rack_history_2026.md)에 있다. 사용자에 따르면 큰 구조는 유지되었다.
바뀐 것은 번호 체계 변경, 특정 렉 철거, 통로 통합 같은 수준이다. 각 렉의 방문 비중(주문-렉 쌍 기준)을 색 농도로 표시한다. 할당 로케이션
기준이며 실제 피킹 시각·경로가 아니다.

2026-10-14 사용자가 분석 방법을 질문하여 [입출고 분석 계획안](mfc_analysis_plan.md)을 작성했다.
이는 제안된 접근법이며 실행 결과나 확정된 요구사항은 아니다. 데이터 분석은 아직 시작하지 않았다.

## 1. 확인된 현재 운영

### 센터와 시간 목표

- 우아한 청년들이 운영하는 도심형 MFC(Micro Fulfillment Center)다.
- 서비스 목표는 30분 이내 배송 완료다. 30분의 정확한 기산 시점은 아직 확인하지 않았다.
- **출고 완료는 배송기사에게 인계한 시점**을 뜻한다. 패킹 완료와 구분한다.
- 출고 요청 후 10분 내 출고 완료를 지향하지만, 기사 도착 시각 등 변수가 있으므로
  **센터 기준은 10분 이내 패킹 완료**, **현재 센터의 운영 목표는 8분 이내 패킹 완료**다.
- 시간의 기산점은 작업 시작 버튼을 누른 시점이 아니라 출고 요청 시점이다.
  요청 후 작업 배정·시작까지의 대기시간과 피킹·복귀·패킹 시간을 포함한다.
- 사용자 설명에 따르면 인원과 주문 수에 따라 차이가 있지만, **6~8분이 현장에서 보는
  통상적인 적정 범위**다. 이는 실측 평균·분포나 최소 소요시간을 뜻하지 않는다.
  6분 미만을 부적정 처리로 분류하지 않는다.
- 사용자는 적정 범위를 초과하는 상황의 요인으로 인원 부족, 미숙련 인원 비중 증가,
  갑작스러운 주문 집중 등을 들며, 현장 작업 중 즉시 통제하기 어려운 조건으로 설명했다.
  이 설명만으로 모든 8분 초과 건의 원인을 확정하거나 분석에서 제외하지 않는다.
- 이 시간들은 운영 기준·목표와 현장의 판단이다. 실제 준수율이나 원인별 영향이
  데이터로 확인되었다는 뜻은 아니다.

분석에서 사용할 시간 구분:

| 구간·지표 | 시작 → 종료 | 해석 |
| --- | --- | --- |
| 센터 처리시간 | 출고 요청 → 패킹 완료 | 현재 목표 8분 이내, 센터 기준 10분 이내, 현장 적정 범위 6~8분 |
| 패킹 후 인계까지의 시간 | 패킹 완료 → 배송기사 인계 | 기사 도착 등 여러 변수가 작용하므로 피킹·패킹 시간과 분리 |
| 출고 완료까지의 시간 | 출고 요청 → 배송기사 인계 | 센터 처리시간과 패킹 후 인계까지의 시간을 합한 구간 |

8분 목표 초과와 10분 기준 초과는 별도로 집계한다. 지연 원인을 비교할 때는 해당 시점의
인원 수, 숙련도 구성, 주문 유입량 등의 조건을 함께 확인한다. 인력·숙련도 요인을
장기적인 운영 개선으로도 바꿀 수 없는 조건이라고 단정하지 않는다.

### 주문 할당: 현장 명칭 ‘릴레이 방식’

- 대기 주문은 **출고 예상 시간 오름차순**으로 처리 우선순위가 정해진다.
- 작업 시작을 먼저 누른 작업자에게 우선순위에 따른 주문이 할당된다.
- 작업자는 상품 부피·무게·존과 관계없이 고객의 장바구니에 담긴 상품들을 피킹한다.
- ‘출고 예상 시간’과 ‘출고 요청 시각’은 별도 용어다. 두 값이 같은 순서를 만든다고
  가정하지 않는다. 사용자는 출고 예상 시간을 시스템이 별도로 계산하는 것으로 이해하고
  있으나, 상세 로직은 알지 못한다. 요청 시각 + 10분으로 대체하지 않는다.
- **미확인 추측:** 사용자는 포장된 무게에 대한 예상값이 존재하며 이 값이 출고 예상 시간에
  어느 정도 반영되는 것 같다고 설명했다. 무게 반영 여부·방향·산식은 확인되지 않았으므로
  할당 로직의 확정 조건으로 사용하지 않는다.
- 현재 센터의 릴레이 방식은 **작업 시작 → 우선순위에 따른 주문 하나 할당 → 해당 주문
  전체 피킹 → 공통 패킹 구역 복귀 → 같은 작업자가 패킹·완료 → 다음 주문**이다.
- 여러 주문을 동시에 처리하는 방식도 있지만, **현재 센터는 채택하지 않는다.**
- ‘릴레이’라는 명칭을 존별 분담이나 작업자 간 순차 인계로 해석하지 않는다.
  비정상 상황의 인계·지원 예외 여부는 별도로 확인하지 않았다.

### 규모와 공간

- 취급 SKU는 약 **15,000개**다. 이는 사용자 설명에 따른 대략적인 운영 규모다.
- 소규모 임대형 센터로, 증축에는 물리적 한계가 있다.
- 모든 상품을 수평적으로 진열할 수 없어 수직 공간도 사용한다.
- 사용자는 구역 구조를 **‘(상온)–(패킹 구간)–(냉장)–(냉동)’의 수직적 구조**라고 설명했다.
  이는 설명된 배치 순서를 기록한 것으로, 실제 층간 배치인지 도면상의 세로 배치인지는
  아직 확정하지 않는다. 이후 전체 구조 PNG와 로케이션 개략도가 제공되었다.
- **공통 패킹 구역은 센터 가운데, 냉장 구역과 상온 구역 사이**에 있다.
  그림상의 정확한 경계·좌표와 두 그림 간 상세 대응은 아직 확인하지 않았다.
- 상온은 패킹 구역에 가까운 C 히트맵 뒤로 **D 랜덤 진열 공간이 길게 이어진다.**
  이전에 제공된 전체 구조 그림은 상온의 히트맵과 일부 구간만 보여주었으며,
  상온 전체 범위는 2026-10-15 추가 사진으로 보완되었다.
- 증축 제약이 내부 진열 변경이나 동선 변경까지 모두 금지한다는 뜻은 아니다.
  변경 가능한 범위는 아직 확인하지 않았다.

| `I` | 이전 표기. 현재는 모두 `A`로 대체됨 |
| `W` | 이전 냉동 구역 표기. 현재는 모두 `A`로 대체됨 |

`I`·`W`의 대체 사실은 현재 구역을 이해하기 위한 설명이다. 변경 시점이나 개별 로케이션의
이력상 대응은 아직 확인하지 않았으며, 과거 원본 데이터의 코드를 일괄 치환한 것은 아니다.

**구역 코드의 시기별 의미 변경(2026-10-15 사용자 확인)**

- **C 구역이 등장하기 전에는 A가 상온 구역을 의미했다. 현재 A는 냉동 구역이다.**
- C 도입 시점과 A의 냉동 전환 시점, I·W의 A 통합 시점 사이의 정확한 관계는 미확인이다.
  이 변경들이 모두 같은 날 발생했다고 가정하지 않는다.
- 과거 입출고 데이터와 도면의 A를 현재 기준으로 모두 냉동으로 해석하지 않는다.
  코드 의미는 해당 자료의 시점과 변경 이력을 함께 확인해야 한다.
- 과거 A와 현재 C·D 사이의 개별 로케이션 대응은 확인되지 않았다.
  과거 A를 C 또는 D로 일괄 치환하지 않는다.

### 피킹 경로

- 작업자마다 실제 피킹 순서는 다르다.
- 기본 원칙은 **S-Shape 패턴**이다. 복도를 S자 형태로 지나며 그 사이에 있는 상품을 피킹한다.
- 모든 작업자가 동일한 경로를 따르거나 모든 복도를 반드시 통과한다고 가정하지 않는다.
  빈 복도 생략, 진입 방향, 예외 경로는 아직 확인하지 않았다.
- 사용자는 대부분 상품을 효율적으로 피킹하더라도 장바구니에 포함된 한두 개 이상의
  상품이 먼 곳에 있으면 해당 위치를 방문해야 한다는 점을 강조했다.
  전체 동선에는 해당 방문과 공통 패킹 구역으로 돌아오는 경로가 포함된다.

### 진열

- 현재 기본 방식은 **랜덤 진열**이다.
- 일부 고정 진열과 특정 상품군의 위치 고정을 함께 사용한다.
- 로케이션에는 다음과 같은 시스템 제한을 설정할 수 있다.
  - 소비기한(사용자 표현상 제조기한 포함) 중복 허용 또는 금지.
  - 중복을 허용할 때 허용 개수 설정.
  - 해당 로케이션에 진열할 SKU 수 제한: 0, 1, 2, 3, ….
- 소비기한 중복 허용 개수 2는 **동일 SKU의 서로 다른 소비기한 물량 두 종류까지
  같은 로케이션에 진열 가능**하다는 의미다. 낱개 재고 수량을 2개로 제한한다는 뜻이 아니다.
- **SKU 수 제한 0은 해당 로케이션 진열 불가**, **1은 한 종류의 상품(SKU)만 진열 가능**을 뜻한다.
- 기존의 ‘시스템에 진열 제한이 없다’는 설명은 후속 설명으로 보완한다.
  **소비기한·SKU 수 설정은 존재하지만, 렉 옆 적재에 따른 통로 침범이나 물리적 적재 상태를
  감지·제한하는 로직은 없다.** 앞서 사용자는 상온 상품을 냉동에 진열해도 시스템이
  감지하지 않는다고 설명했다. 이 온도대 감지 부재와 위 설정의 존재는 구분한다.
- 시스템의 감지·제한 부재가 실제로 모든 위치에 진열해도 된다는 뜻은 아니다.
  현장의 온도대·상품군별 운영 규칙과 고정 진열 대상은 별도 확인이 필요하다.
- 랜덤 진열이라는 설명만으로 위치가 균등 무작위로 배정되거나 SKU당 위치가 하나라고
  가정하지 않는다.
- 사용자가 설명한 **시스템의 피킹 우선순위는 ‘소비기한이 짧은 순 → 로케이션 정보
  오름차순’**이다. 작업자에게 주문을 배정하는 출고 예상 시간 순서와 구분한다.
- 피킹할 때 소비기한은 **육안으로 확인**한다. 이 설명을 상품 바코드 등 다른 모든 항목에
  스캔 검증이 없다는 의미로 확대하지 않는다.

### 현재 히트맵 운영

- 센터는 1년·1달 등의 출고 데이터를 기반으로 ‘히트맵’이라는 개념을 사용한다.
- **사용자가 얻은 정보에 따르면 기준은 단순 출고 수량의 합계**다.
  사용자는 정확한 정보를 확인한 것은 아니라고 밝혔으므로, 확정된 시스템 산식으로 기록하지 않는다.
- 사용자가 설명한 기본 방식은 **출고량이 많은 상품은 앞에, 적은 상품은 뒤에 배치**하는 것이다.
- **히트 구간은 패킹 구역과 가까운 위치**를 뜻한다. 구체적인 경계와 수용량은 미확인이다.
- 갱신은 관리자가 직접 수동으로 수행한다. 1년·1달은 출고 데이터를 보는 기간의 예시이며,
  자동 갱신 주기나 고정된 갱신 주기를 의미하지 않는다.
- 관리자는 작업 효율과 공간 특성을 고려하면서 불가피한 비효율을 선택하기도 한다.
- 이 문서의 ‘히트맵’은 위 현장 운영 개념을 뜻한다. 앞서 노트북에서 만든 시각화와
  동일한 지표·구역 정의·시스템 기능이라고 단정하지 않는다.

### 로케이션 코드와 렉 옆 진열 표시

- 대용량 진열에도 해당 렉 번호와 위치 정보를 남긴다.
- 사용자 제공 예시 `A01-01-105`의 의미는 다음과 같다.

| 구성 | 예시 값 | 사용자 설명 |
| --- | --- | --- |
| 존 | `A` | 현재 기준 냉동 존. C 도입 전 A는 상온을 의미했음 |
| 복도 | 첫 번째 `01` | 01번 복도 |
| 렉 | 두 번째 `01` | 01번 렉 |
| 층 | 마지막 묶음의 `1` | 1층, 맨 아래 층 |
| 선반 | 마지막 묶음의 `05` | 5번째 선반 |

- 렉 옆에 로케이션을 크게 표시하고 해당 구역에 상품을 진열하도록 운영한다.
- 이 표는 사용자가 설명한 예시를 기록한 것이다. 다른 코드의 의미나 별도 예외 규칙은
  이번 답변에서 설명되지 않았다.
- 렉 번호 증가 방향, 복도 양쪽 번호 규칙, 복도 간 연결은 제공된 이미지의 설명을 통해
  확인한다. 아래 번호 방향은 2026-10-15 후속 답변으로 확정되었다.

### 렉 한 칸 단위 지도: 2026-10-15 확인

- 목표는 **알파벳 한 칸 = 존·복도·렉 코드 하나**다. 예를 들어 `A01-01-105`와
  `A01-01-205`는 같은 `A01-01` 칸으로 묶는다. 층·선반은 제외한다.
- 일반 복도 기준으로 **A·B는 그림 아래쪽 진열면이 홀수, 위쪽 진열면이 짝수**다.
  **상온 C·D는 반대로 아래쪽이 짝수, 위쪽이 홀수**다(2026-10-15 사용자 정정).
- **A·B의 렉 번호는 왼쪽→오른쪽**, **C·D는 오른쪽→왼쪽**으로 증가한다.
  사용자가 B·C·D 방향을 정정했으므로 앞선 B=오른쪽→왼쪽, C·D=왼쪽→오른쪽
  설명은 적용하지 않는다. B09는 별도로 위→아래 01~06을 유지한다.

| 존 | 복도 번호의 그림상 배치 | 별도 위치 |
| --- | --- | --- |
| A | 아래→위로 A01~A11 | 오른쪽 위에 세로로 `##A`가 있는 부분의 A는 A12 |
| B | 아래→위로 B00~B08 | 오른쪽 입구 근처의 일자 공간이 B09, 위→아래로 B09-01~06 |
| C | 아래→위로 C00~C08 | C08-00의 위치는 확인 대기 |
| D | 위→아래로 D00~D08 | C와 같이 위쪽 홀수·아래쪽 짝수 |

- 9월 출고에서 `A12-00`, `B09-01~06`, `B08-00`, `C08-00`이 관측되었다.
  **B08-00은 B08-02 바로 왼쪽**이다(2026-10-15 사용자 확인). C08-00은 위치 확인 후 반영한다.
- **D07-01은 현재 철거된 렉**이다. 사용자 지시에 따라 과거 출고를 표시하려고 지도에는
  있는 것으로 둔다(`placement=assumed_removed`). 현재 렉으로 세지 않는다.
- 출고 기록은 9월 1~27일에 한정된다. 관측 번호 사이의 누락은 렉 부재나 기둥을 뜻하지
  않는다. 출고가 없던 렉까지 모두 확인된 것으로 간주하지 않는다.
- **사용자 확인: 현재 지도에서 렉이 끊기고 `.`으로 표시된 공간은 모두 교차 통로다.**
  `#`은 통행을 막는 기둥이다. 통로 위치는 기존 배열의 `.`·`#` 배치를 기준으로 보존한다.
  `?`·`U`는 확인된 통로로 취급하지 않는다. 이는 상대 격자의 통행 규칙이며 실제 폭은 아니다.

**구현 결과와 근사(사용자 확인 사실과 구분)**

- 출고에서 관측한 렉 402개 중 401개와 철거된 D07-01을 코드별 칸으로 표시했다.
  C08-00은 위치 확인 대기 목록으로 분리했다. 중간 미관측 번호는 16개이며 `~`로 표시한다
  (D07-03·05 추가).
- 기존 통로·기둥의 영역을 바꾸지 않고 연속 렉 영역을 칸으로 나눴다.
  각 면에서 코드 자리를 구간 길이 비율로 배분하므로, **개별 렉 경계·번호 위치는 근사**다.
- 복도별 위·아래 면은 기존 그림 행에 대응시킨다. A 20행·B 23행은 맞닿은 두 면으로
  보고 높이를 반씩 사용한 구현상 가정이다. 사용자 확인값으로 취급하지 않는다.
- 원본의 코드 미배정 렉 영역은 남겨 둔다. 새 배열은 한 행에 렉 칸 하나의 코드·상대 좌표·
  너비·높이를 담으며 칸 크기가 균일하지 않다. 배열 인덱스 차이를 거리로 사용하지 않는다.
- [레이아웃 설명](mfc_layout_array.md)에 재생성 방법·출력 파일·근사를 기록했다.

- 반복된 번호는 같은 복도를 향한 양쪽 진열면을 나타내는 것으로 보이나, 사용자 확인 전이다.

- `I`·`W`는 기존 냉동 구역이며 현재 A로 대체되었다. 다만 **C 도입 전 A는 상온**이었다는

  색상의 별도 의미와 변경 후 개별 번호 대응도 미확인이다.
- 패킹 구역의 상대적 위치는 확인되었으나, 그림 내 정확한 경계·좌표, 개략도가 전체 구조 중
  어느 부분인지, 실제 출입구와 통로 연결, 축척·실제 폭·길이는 아직 확정하지 않는다.

### 추가 상온 전체 이미지: 2026-10-15

### 피킹 후 패킹과 복귀

- **피킹한 작업자가 패킹까지 직접 수행하는 것이 원칙**이다.
- 패킹 장소는 **센터 가운데 냉장·상온 구역 사이에 있는 고정된 공통 패킹 구역**이다.
- 피킹을 마친 작업자는 **시작 지점인 공통 패킹 구역으로 반드시 복귀**한다.
- 2026-10-16 사용자 확인: 모두가 B와 C 사이의 공통 장소에서 출발하고 그곳으로 돌아온다.
  이 장소는 B09와 가장 가깝고, 상온에서는 C04~C06과 가장 가깝다.
  도면별 정확한 대표 좌표·출입 연결거리는 아직 미확인이다.
- 2026-10-16 사용자 확인: A–B–패킹·피킹 시작 구역–C–D 구조다.
  A에 가려면 반드시 B를, D에 가려면 반드시 C를 통과한다.
  A 입구는 A06~A08 사이이고, B에서 A로 향하는 출구는 B04 방향이다.
- 동선 분석에서는 마지막 피킹 위치에서 공통 패킹 구역까지의 복귀 구간을 포함해야 한다.
- 구역 내 패킹대의 개수·배정·선택 규칙은 아직 확인하지 않았다.
  공통 구역이라는 설명을 단일 패킹대 또는 정확히 동일한 좌표로의 복귀로 단정하지 않는다.

## 2. 사용자 관측 문제와 개선 방향

### 현재 문제: 사용자 현장 관측

- 물리적 공간 한계 때문에 모든 상품을 렉의 로케이션에 수용하기 어렵다.
- 렉에 넣지 않고 **렉 옆에 적재하는 형태의 진열**이 자주 발생한다.
  주로 대용량으로 들어오거나 부피가 큰 상품이 해당한다.
  ‘대용량’이 개별 상품 규격인지 한 번에 들어오는 물량인지와 대상 판별 기준은 미확인이다.
- 이 적재로 작업자 이동 통로가 좁아지고 충돌 위험이 높아진다고 사용자가 설명했다.
- 사용자는 실제로 많은 작업자의 정강이에 멍과 상처가 있다고 보고했다.
  이는 현장 관측이며 발생 건수·비율·원인별 상해 통계는 확보하지 않았다.
- 렉 옆 적재에도 렉 번호·위치 정보를 가진 로케이션을 표시해 해당 구역에 진열한다.
  코드 구성은 위 ‘로케이션 코드와 렉 옆 진열 표시’ 절에 기록했다.
  렉 내부와 렉 옆 적재를 별도 표식으로 구분하는지 여부는 이번 답변에서 설명되지 않았다.

### 추가 문제: 분산·복귀 동선·배치 판단

다음은 사용자가 추가로 설명한 문제 인식이며, 이 문서에서 분석한 결론이 아니다.

1. **원거리 상품 방문과 복귀 경로:** S-Shape로 대부분의 상품을 효율적으로 피킹해도,
   장바구니의 일부 상품이 먼 곳에 있으면 그 위치를 방문해야 한다.
   사용자는 센터 동선 길이를 볼 때 돌아오는 경로까지 고려해야 한다고 강조했다.
2. **진열과 피킹 효율의 연결 부족:** 사용자는 진열 작업자가 피킹 작업자의 효율을
   고려하지 않고 진열하는 문제를 설명했다. 상품이 멀거나 흩어진 위치에 놓일 수 있으며,
   시스템에서 이를 보정하지 않는다.
3. **수직 공간을 포함한 배치 판단 로직 부재:** 수평 공간만으로 상품을 수용할 수 없어
   수직 진열을 병행한다. 이 공간 안에서 어떤 상품을 패킹 구역 가까이에 두고 어떤 상품을
   멀리 둘지 결정하는 시스템 로직이 없다. 이는 관리자의 수동 히트맵 운영과 구분한다.
4. **장바구니 구성의 예측 한계:** 작업자는 고객의 장바구니 전체를 대신 피킹한다.
   사용자는 과거 출고 데이터를 분석하더라도 미래의 장바구니 구성을 정확하게 예상할 수
   없다고 설명했다. 따라서 장바구니에 포함될 상품이 최대한 히트 구간에 있도록 진열하는
   방향을 생각하고 있다. 히트 구간의 구체적인 경계·수용량은 아직 설명되지 않았다.
5. **히트맵의 수동 갱신과 운영상 절충:** 출고량에 따라 앞·뒤 배치를 정하는 현행 히트맵은
   관리자가 직접 갱신해야 한다. 작업 효율과 공간 특성을 함께 고려하다 보면 불가피한
   비효율을 선택할 수 있다는 설명이다. 이를 모두 단순 배치 실수로 기록하지 않는다.

### 추가 문제: 할당 위치 이탈과 유사 상품의 인접 진열

- 사용자는 상품이 흩어져 있으면 작업자가 **할당된 로케이션 대신 눈에 보이는 상품을
  가져가는 경우가 많다**고 설명했다. 발생 빈도는 사용자 관측이며 수치로 확인하지 않았다.
- 소비기한이 짧은 상품을 지시받았지만 다른 소비기한의 실물을 집으면,
  **시스템에서 차감된 재고와 실제 출고된 상품의 소비기한이 달라질 수 있다.**
  사용자는 이 상황이 앞서 언급한 소비기한 혼적의 출고 오류라고 확인했다.
- 사용자는 추가로 **비슷한 상품이 얼마나 가까이 진열되어 있는지** 파악하고,
  **인접 진열에 따른 위험도**를 판단할 필요가 있다고 설명했다.
  이는 동일 SKU의 소비기한 혼재와 함께 기록할 별도의 관심 사항이다.
- ‘비슷한 상품’의 판별 기준과 ‘가까움’의 범위는 아직 정하지 않았다.
  현재는 문제 인식만 기록하며 유사도·인접도·위험도를 계산하지 않는다.

### 향후 분석의 순서와 목적

- **물리적 적재 문제를 감지하는 로직을 작성하기 전에**, 기존 데이터로 상품들이 얼마나
  흩어져 있는지 파악하는 것이 사용자가 제시한 선행 분석이다.
- 사용자가 파악하려는 ‘흩어짐’은 **동일 SKU가 얼마나 여러 위치에 분산되어 있는가**다.
  확장해서 **실제 출고 데이터에서 할당된 로케이션 정보를 바탕으로 동선이 얼마나
  흩어지는가**를 파악하려는 의도다.
- 이는 향후 분석 목적의 기록이다. 현재는 사용자의 요청에 따라 설명만 기록하며 분석하지 않는다.
- 추가 설명에는 원거리 상품까지 방문한 뒤 복귀하는 동선, 수직 공간을 포함한 근거리·원거리
  배치 판단, 장바구니 상품이 히트 구간에 포함되도록 하는 방향과 수동 갱신 부담도 포함된다.
  구체적인 해결 로직이나 지표는 아직 정하지 않았다.
- 유사 상품의 인접 진열 현황과 위험도도 향후 관심 대상으로 추가되었다.
- 앞선 냉장 TOP 15 분석의 대상·순위를 이번 분석에 자동 적용하지 않는다.
  이번 설명에서는 대용량·부피가 큰 상품을 언급했으며 온도대 범위는 확정하지 않았다.

### 제안한 개선안: 압축진열

- 압축진열은 **동일 SKU의 서로 다른 소비기한 물량을 하나의 로케이션에 합치는 것**이다.
  여러 SKU를 함께 섞는 제안으로 해석하지 않는다.
- 앞선 설명에서는 대용량·부피가 큰 상품을 특정 구역에 모아 적층하고,
  위에서 아래로 피킹하도록 유도하는 방식을 제시했다.
- 사용자는 시스템이 ‘소비기한이 짧은 순 → 로케이션 정보 오름차순’으로 피킹 우선순위를
  정하므로, 같은 SKU를 한 곳에 모으면 분산을 줄이고 진열 공간 효율을 높일 수 있다고 설명했다.
- **사용자가 기대하는 효과:** 오피킹 감소, 공간 활용 향상, 로케이션 및 동선의 분산 감소.
  이는 제안의 취지이며 이 문서에서 데이터 분석으로 검증한 결과는 아니다.
- **사용자가 인식한 트레이드오프:** 소비기한이 다른 물량의 혼적으로 출고 오류가 발생할
  위험이 있으며, 사람이 소비기한을 육안으로 꼼꼼히 확인해야 한다.
- 확인된 오류 유형은 **지시된 소비기한과 다른 실물을 피킹하여 시스템 재고 차감과
  실제 출고 상품의 소비기한이 불일치하는 것**이다. 허용 범위는 정하지 않았으며,
  소비기한 경과 상품의 출고를 허용한다는 의미로 확대하지 않는다.
- 현재 채택된 운영 방식이 아니라 **검토할 개선안**이다. 통로 확보, 피킹 시간 단축,
  공간 사용 감소 효과는 아직 검증되지 않았다. 적층 높이·하중·대상 구역도 미정이다.

| 렉 옆 적재 | 사용자 관측상 통로 축소·충돌 위험 문제 존재 | 코드만으로 실제 적재 형태와 통로 폭을 알 수 있음 |

현재 운영 방식은 분석의 기준 상황이다. 어떤 조건을 개선안에서도 반드시 유지해야 하는지는
사용자에게 확인해야 하며, 현재 운영 설명을 모두 변경 불가능한 제약으로 바꾸지 않는다.

## 4. 기존 데이터와 연결할 때의 한계

이 절은 앞선 입출고 분석에서 확인한 데이터 기준이며, 위 운영 설명과는 출처가 다르다.

- 기존 입고 분석은 `receivingQuantity`를 수량으로, `shippingScheduledDate`를 날짜로 사용했다.
  날짜는 예정일이며 실제 입고 완료 시각이 아니다.
- 기존 출고 수량 분석은 `status == SHIPPED`인 행의 `pickingQuantity`를 합산했다.
  `outboundRequestDateTime`은 출고 요청 시각이며 실제 출고 완료 시각이 아니다.
- 현재 확인한 outbound CSV 열에는 작업자 ID, 작업 시작 시각, 피킹 완료 시각,
  패킹 완료 시각, 배송기사 인계 시각(실제 출고 완료 시각)이 없다.
  따라서 이 CSV만으로 패킹 완료 8분 목표·10분 기준 준수율, 기사 인계까지의 시간,
  작업자별 피킹·패킹 소요시간을 계산할 수 없다.
- 인원 부족·숙련도·주문 집중의 영향을 구분하려면 근무 인원과 숙련도 등의 추가 자료가
  필요하다. 출고 요청 건수만으로 인력 상태나 지연 원인을 확정할 수 없다.
- `locationCode`는 있지만, 코드만으로 통로 연결·좌표·이동거리·패킹대 위치를 확정할 수 없다.
- A의 의미는 과거 상온에서 현재 냉동으로 달라졌다. 코드 접두사만으로 과거 데이터의
  온도대를 판정하지 않는다. 시기별 코드 이력과 원본 온도대 열의 의미를 함께 확인해야 한다.
- 사용자가 할당 위치와 다른 곳에서 상품을 가져가는 사례를 설명했으므로,
  **출고 데이터의 할당 로케이션을 실제 방문 위치나 실물 반출 위치와 항상 같다고 보지 않는다.**
  할당 위치를 기준으로 한 기록과 실제 행동의 차이를 구분해야 한다.
- 출고 기록으로는 SKU별로 **해당 기간 출고 행에서 관측된 로케이션 수**와 위치별 출고량을
  집계할 수 있다. 장기간 여러 위치에서 출고되었더라도 위치 이동·재진열의 결과일 수 있으므로
  같은 시점에 여러 위치를 점유했다고 단정할 수 없다. 출고가 없던 재고 위치도 보이지 않는다.
- 동시 분산을 확인하려면 시점별 로케이션·SKU·재고 수량 스냅샷이나, 기준 재고와 누락 없는
  재고·이동 이력 등이 필요하다. 현재 입출고 CSV만으로 동시 점유 현황을 재구성한다고
  가정하지 않는다.
- inbound의 `displayLocationCode`와 outbound의 `locationCode`가 실제로 같은 공간·시점의
  위치를 가리키는지 확인하기 전에는 둘을 동일한 진열 이력으로 합치지 않는다.
- 현재 CSV에는 상품 외형 치수·적재 부피·렉 수용량·실제 통로 폭이 없다.
  상품명에 표시된 용량이나 입고 수량만으로 물리적 부피·통로 침범을 확정할 수 없다.
- **2026년 6~9월 출고에서 관측한 코드 전환(데이터 관측, 사용자 미확인):** C는 7/4 전후부터
  나타나고, 6/1~7/4의 A(C 도입 전 상온 A로 보임)는 7/6 주부터 거의 사라진다. X는 7/25,
  I·W는 8/9 이후 관측되지 않는다. B는 7/13 주부터 본격 사용되고, A는 7/27 주부터
  다시 늘어난다(현재 냉동 A로 보임). D는 기간 내내 비슷한 규모다. 현재 레이아웃
  (`layout_2026-09`)에 연결되는 행은 6월 26%, 7월 54%, 8월 96%, 9월 99%다.
  `storageTemperature`는 6월의 상온 A 행에도 `FROZEN`으로 기록되어 있다.
  행이 기록된 시점의 온도대를 나타낸다고 보지 않는다.
- **2026년 렉 코드 이력(11 노트북, 데이터 관측·사용자 미확인):** 5/25 주에 D 코드 95개가
  처음 나타나고, 옛 A의 높은 번호(대략 13 이상) 73개가 끊긴다. 6/29 주에는 C 코드 100개가
  나타나고 남은 옛 A 47개가 끊긴다. 7/13~7/20 주에는 B 84개가 나타나고 X 84개가 끊긴다.
  P1의 X 복도별 번호는 현재 B와 비슷하다. 예를 들어 X08과 B08은 `00-04,06-12,14,16,18`로 같다.
  7/27~8/3 주에 A가 A01~A12로 다시 나타나고(옛 번호 재사용 72개, 신규 21개) I·W가 끊긴다.

## 6. 문서 갱신 규칙

1. 사용자가 조건을 추가·수정하거나 질문에 답하면 해당 본문을 갱신한다.
2. 답변된 질문에는 답변 요지와 확인 날짜를 남기고 상태를 변경한다.
3. 사용자 확인 사실, 데이터에서 관측한 사실, 분석을 위한 가정을 구분한다.
4. 새로운 설명이 기존 설명과 충돌하면 어떤 조건이 적용되는지 확인한다.
   수정이 명확한 경우 현재 본문을 바로 수정하고 변경 이력에 이전 내용과 변경 이유를 남긴다.
5. 용어에 대한 설명이나 해석이 새로 확인되면 대화에만 남기지 않고 관련 본문에도 반영한다.
6. 새 분석을 시작하는 에이전트는 이 문서와 확인 대기 사항을 먼저 읽는다.
